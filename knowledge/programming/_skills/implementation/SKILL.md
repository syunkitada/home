# 実装

ユーザーが求めた変更を、既存の仕様・利用経路・リポジトリ規約に沿って実装する。実装依頼だけではコミット、push、PR 投稿を行わない。

## 手順

1. ユーザーの要件、対象範囲、完了条件、変更してはいけない範囲を確認する。
2. 適用される `AGENTS.md`、README、仕様、既存の実装、関連テストを読む。作業ツリーの既存変更を確認し、無関係な変更を上書きしない。
3. 変更を小さな実装単位へ分け、必要なら実装前に受け入れ条件と検証方法を整理する。
4. 既存の命名、エラー処理、設定、データ形式、依存関係を維持し、必要最小限の範囲だけを変更する。
5. ファイルやディレクトリの追加・削除・移動・改名、構成を示す README・目次・ファイル一覧・相対リンクの変更、または役割変更を伴う場合は、適用される `AGENTS.md` と README の規約を確認し、関係する README、構成説明、相対リンクを同じ変更で更新する。生成物、ローカル専用ファイル、未追跡の一時ファイルは、適用される規約で対象外なら構成説明の一覧やナビゲーションに含めない。
6. 挙動を変更する場合は、リポジトリのテスト方針に従って回帰テストまたは受け入れテストを追加・更新する。テスト駆動で進める場合は、`tdd` の RED、GREEN、REFACTOR 手順を適用する。
7. 変更した経路に対して、最も狭い有効なテスト、型検査、lint、build などを実行する。ドキュメントや構成の変更では、リンク先、配置、構成説明の記載対象も確認する。実行できない確認は理由を記録する。
8. 差分、作業ツリー、テスト結果、未確認事項を確認して報告する。完了を主張する前に、実行した検証の結果を根拠にする。

## 境界

- レビューだけの依頼では変更しない。レビューは `code-review` の対象とする。
- 失敗の原因究明を主目的とする依頼では、推測で修正を重ねず、再現・切り分け・根本原因の確認を優先する。原因が確定していない場合は、確定した原因として報告しない。診断だけの依頼ではコードを変更せず、原因、証拠、未解決事項を報告する。
- README、構成説明、相対リンク、ディレクトリ構成の同期も、この skill の責務として扱う。
- commit、push、branch、PR の作成は、ユーザーが明示した場合だけ `git-workflow` の手順で行う。
- 破壊的な reset、削除、履歴書き換えは、対象と復旧方法を確認せずに行わない。
