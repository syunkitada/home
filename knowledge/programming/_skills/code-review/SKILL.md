# コードレビュー

レビュー対象の変更を、仕様・既存の利用経路・リポジトリ規約に照らして調べ、再現可能な不具合や回帰を重要度順に報告する。レビュー依頼だけでは修正、コミット、PR への投稿を行わない。

## 手順

### 1. 範囲を固定する

最初にユーザーの指定、適用される AGENTS.md、作業ツリーの状態を確認する。対象と比較元が指定されていれば、[scope-selection.md](references/scope-selection.md) の対応する範囲だけを使う。PR 番号やリモート PR が指定された場合は、同資料の手順で base と head を解決し、解決できなければ範囲エラーとして報告する。指定がなく作業ツリーに変更があれば、未コミット変更全体を対象にする。

比較元の参照名は解決できる SHA として記録する。不正な参照、空の差分、対象外の変更を確認したら、その時点で範囲を報告する。未追跡ファイルは通常の差分に含まれないため、対象範囲に含む場合は個別に読む。

### 2. 仕様と影響範囲を読む

次の順で根拠を集める。

1. ユーザーが指定した要件・仕様・チケット
2. 変更箇所に適用される AGENTS.md、README、規約
3. 変更された API、設定、データ形式の利用箇所
4. 関連するテスト、エラーハンドリング、移行処理

仕様が見つからない場合は、既存の契約と利用経路を根拠にしてレビューを続け、「仕様未確認」と明記する。仕様の不足だけでレビューを停止しない。

### 3. 変更を評価する

[review-checklist.md](references/review-checklist.md) を読み、変更に関係する観点だけを確認する。少なくとも次を分離して考える。

- **仕様・正しさ**: 要求された挙動、境界値、失敗経路
- **互換性・影響**: 既存の呼び出し元、設定、データ、権限
- **安全性**: 入力検証、認証・認可、秘密情報、外部データ
- **性能・設計**: 無制限処理、不要な I/O、複雑化、依存追加
- **テスト**: 要件を検証するテスト、回帰を捕捉する不足

フレームワーク固有のチェックは、変更内容が該当するときだけ適用する。スタイル上の好みや、今回の変更との因果を示せない既存問題は指摘しない。

### 4. 指摘候補を検証する

候補ごとに、発生条件、到達経路、影響、変更前との差を確認する。必要に応じて [validation-playbook.md](references/validation-playbook.md) の手順で小さな再現や関連テストを実行する。

確認できない推測は確定した指摘として出さない。実行した検証と、コードからの推論を区別する。以前からある問題は、今回の変更で導入・悪化した関係を説明できる場合だけ扱う。

### 5. 結果を報告する

[report-template.md](references/report-template.md) の形式で、重要度の高い順に報告する。各指摘には重要度、確信度、ファイルと行、発生条件、影響、根拠、可能なら修正方針を含める。

指摘がない場合も、対象範囲、読んだ根拠、実行した検証、未確認事項を報告する。修正が必要な場合は、レビュー結果と実装作業を分けて次の依頼として扱う。
