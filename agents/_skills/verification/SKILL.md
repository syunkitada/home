# 完了前検証

「完了した」「修正できた」「テストが通った」と報告する前に、主張を裏付ける新しい検証を実行する。過去の実行結果や、コードを変更した事実だけで成功を推測しない。

## 手順

1. 完了条件、対象範囲、変更された経路を確認し、それぞれを検証するコマンドまたは確認方法を決める。
2. 最も狭い有効なテスト、型検査、lint、build、起動確認などを実行する。ドキュメントや設定変更では、リンク、構文、形式、配置、参照先を確認する。
3. 重要な失敗経路、境界条件、既存利用経路を必要な範囲で確認する。テストが通ったことを、未実行経路の証明として扱わない。
4. 全体テストやリポジトリが定める最終検証を実行する。実行できない場合は、理由、代替確認、残るリスクを記録する。
5. `git diff`、`git status`、生成物、意図しない変更を確認し、ユーザーの対象範囲と一致させる。
6. コマンドの終了コードと出力を読み、成功・失敗・未確認を分けて報告する。検証前に完了を主張しない。

## 境界

- 検証だけの依頼では、失敗を隠すために実装を変更しない。
- 無関係な全体テストを、変更の安全性を示す唯一の根拠にしない。
- 破壊的な環境準備や外部サービスへの変更が必要な場合は、代替の読み取り専用検証を優先し、実行できなかったことを明記する。
