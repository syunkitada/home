# 完了前検証

「完了した」「修正できた」「テストが通った」と報告する前に、その主張を裏付ける新しい検証を実行する。過去の実行結果、コードを変更した事実、エージェントの報告だけで成功を推測しない。検証結果は、成功、失敗、未確認を分けて記録する。

## 手順

### 1. 主張と完了条件を分解する

ユーザーの要件、受け入れ条件、対象範囲、完了として報告しようとしている主張を確認する。各主張について、何を実行・確認すれば裏付けられるかを決める。たとえば「バグを修正した」は元の症状を再現するテスト、「テストが通った」は該当コマンドの終了コードと出力、「構成を更新した」はファイル一覧とリンクの確認を必要とする。

テスト、型検査、lint、build、起動確認、手動確認、リンク・構文・配置確認など、変更内容に対応する証拠を選ぶ。全体テストだけで個別の要件を確認できるとは限らない。

### 2. 対象範囲と根拠を固定する

適用される `AGENTS.md`、README、仕様、チケット、計画、既存の利用経路を読み、完了条件と検証対象を確定する。`git status` と `git diff` で、次を分けて確認する。

- ステージ済みの変更
- 未ステージの変更
- 未追跡ファイル
- 生成物、ローカル専用ファイル、意図しない変更

ユーザーが指定した範囲と実際の変更が一致しているか、秘密情報や不要な変更が混入していないかを確認する。レビュー依頼の場合は [code-review](../code-review/SKILL.md) の対象範囲・証拠基準を使い、検証 skill が修正を始めない。

### 3. リポジトリの検証方法を発見する

README、CI、Makefile、`package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml` などから、標準の focused test、関連スイート、全体テスト、型検査、lint、build、起動確認のコマンドを調べる。標準コマンドを推測せず、チェックインされたラッパーやプロジェクト固有のコマンドを優先する。

破壊的な環境準備、外部サービスへの変更、認証情報が必要な操作が避けられない場合は、読み取り専用の代替確認を優先し、実行できなかった範囲と残るリスクを記録する。

### 4. 最も狭い有効な検証を実行する

変更された経路に対して、まず最も狭い有効なテスト、型検査、lint、build、リンク・構文確認などを実行する。変更内容に応じて次を選ぶ。

- 挙動変更: focused test、関連回帰テスト、必要な境界・失敗経路
- バグ修正: 元の症状を再現する回帰テストと、関連経路
- 文書・構成変更: Markdown構文、相対リンク、Index、配置、ファイル一覧
- 設定変更: 設定構文、適用先、起動または読み込み確認、既存設定との互換性
- 依存・build変更: 型検査、lint、build、最小の起動またはパッケージ確認

コマンドごとに終了コードと出力を読み、実際に何が確認できたかを記録する。コマンドが失敗した場合は、失敗を隠すために実装やテストを変更しない。

### 5. 境界と既存経路を確認する

要件に関係する正常系、失敗経路、境界値、互換性、既存利用経路、統合経路を必要な範囲で確認する。テストが通ったことを、テストされていない経路の証明として扱わない。テストがない場合も、静的確認、手動確認、再現手順、ログ、差分など、主張に最も近い代替証拠を選び、未確認の部分を残す。

### 6. 最終検証を実行する

現在の変更状態で、リポジトリが定める全体テスト、最終lint、build、型検査、リンク検査などを実行する。実装中や過去のセッションで成功した結果を、変更後の最終結果として流用しない。検証コマンド自体が対象範囲を十分に含むか確認し、実行できない場合は理由、代替確認、残るリスクを明記する。

### 7. 証拠に基づいて報告する

要件または主張ごとに、次の形式で結果を整理する。

- **確認済み**: 実行したコマンドまたは確認方法、終了コード、重要な出力
- **失敗**: 失敗したコマンド、症状、影響、切り分け状況
- **未確認**: 実行できなかった確認、理由、代替確認、残るリスク
- **差分状態**: 対象ファイル、未追跡ファイル、意図しない変更の有無

証拠がない主張は成功として報告しない。「おそらく」「問題なさそう」などの推測で完了を表現せず、検証後の実際の状態を報告する。commit、push、PR、releaseなどは [git-workflow](../git-workflow/SKILL.md) の手順に分ける。

## 境界

- 検証だけの依頼では、失敗を隠すために実装を変更しない。
- 無関係な全体テストを、変更の安全性を示す唯一の根拠にしない。
- 過去の実行結果、コードを変更した事実、他のエージェントの成功報告だけを新しい証拠として扱わない。
- テストが通ったことを、要件の充足、未実行経路の安全性、未確認の境界条件の証明として扱わない。
- 破壊的な環境準備や外部サービスへの変更が必要な場合は、代替の読み取り専用検証を優先し、実行できなかったことを明記する。
- 失敗の原因究明や修正が主目的になった場合は、原因の診断・実装・レビューを対応する skill に分ける。
