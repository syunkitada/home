# 技術説明

対象は、技術記事、README、設計説明、APIやCLIの使い方、トラブルシュート、運用手順です。

## 構成

読者が知りたい結果を最初に示し、必要に応じて次の順で組み立てます。

1. 何ができるか、または何を解決するか
2. 対象読者、前提条件、適用範囲
3. 仕組みや判断理由
4. 実行手順、入力、期待結果
5. 制約、失敗時の扱い、既知の注意点
6. 関連資料や次の手順

文書の種類により、すべての節を作る必要はありません。既存のREADME、設計書、API仕様がある場合は、その構成と用語を優先します。

## 書き方

- 読者が実行する手順は、前提、操作、期待結果を対応させる。
- コマンドやコードは、元の資料や実装から確認できるものだけを載せる。
- APIのパラメータ、戻り値、バージョン、エラー条件は、確認できた範囲で正確に書く。
- 「システムが判断する」のように主体が曖昧な表現は、実装や仕様から主体が分かる場合だけ具体化する。
- 「簡単に」「柔軟に」「安全に」などの評価語は、根拠や具体的な動作がある場合に限って使う。
- 因果関係や条件を、装飾的な箇条書きで分断しない。

技術用語の言い換えで正確さを失わないことを優先します。文章の編集だけで実装やコマンドの誤りを直す場合は、変更した事実を確認事項として示します。
