# 実装

仕様、チケット、または明示された要件を、既存の仕様・利用経路・リポジトリ規約に沿った変更へ変換する。実装、テスト、構成説明の同期、完了前の検証を扱う。計画だけの依頼、レビューだけの依頼、Git の履歴・外部状態の操作は、それぞれ対応する skill に分ける。

## 手順

### 1. 依頼と役割を確定する

ユーザーの要件、対象範囲、完了条件、変更してはいけない範囲を確認する。複数段階の作業や要件が曖昧で、実装方針を決める必要がある場合は、先に [task-planning](../task-planning/SKILL.md) で計画を整理する。

計画だけの依頼では変更を開始しない。レビューだけの依頼は [code-review](../code-review/SKILL.md)、完了可否の確認だけの依頼は [verification](../verification/SKILL.md) を使う。

### 2. 根拠と変更範囲を固定する

次の順で根拠を確認する。

1. ユーザーが指定した仕様、チケット、受け入れ条件
2. 適用される `AGENTS.md`、README、プロジェクト規約
3. 変更箇所の既存実装、呼び出し元、設定、データ形式
4. 関連するテスト、CI、ビルド、エラーハンドリング、移行処理

作業ツリーの既存変更、ステージ済み変更、未追跡ファイルを確認し、無関係な変更を上書き・混入させない。仕様が不足している場合は確認できる契約と利用経路を根拠にし、実装方針を変える不明点は推測で埋めない。

### 3. 受け入れ条件と実装単位を決める

要件を観測可能な受け入れ条件へ分解し、依存関係、リスク、変更対象、検証方法を整理する。複数ファイルにまたがる変更は、最小の完成した縦切り、またはリスクの高い部分から、独立して検証できる単位へ分ける。一つの単位へ無関係な整理や将来向けの一般化を混ぜない。

### 4. 検証方法を決める

テストコマンド、型検査、lint、build、手動確認は README、CI、Makefile、package 設定などから確認し、標準コマンドを推測しない。

- 新しい挙動、バグ修正、既存挙動の変更は、必要に応じて [tdd](../tdd/SKILL.md) の RED、GREEN、REFACTOR を適用する。
- 純粋な文書変更、静的な設定変更、生成物の更新では、TDDを強制せず、リンク、構文、配置、差分、生成物の内容を確認する。
- 各実装単位では最も狭い有効な検証を行い、最後に変更内容に応じた全体検証を行う。

### 5. 最小限の変更を実装する

既存の命名、エラー処理、設定、データ形式、依存関係を維持し、受け入れ条件に必要な範囲だけを変更する。各単位の実装後に、その単位のテストまたは構造確認を実行し、結果を読んでから次へ進む。

ファイルやディレクトリを追加・削除・移動・改名した場合は、適用される規約に従い、関係する README、Index、相対リンクを同じ変更で更新する。生成物、ローカル専用ファイル、未追跡の一時ファイルは、構成説明の対象に含めない。

### 6. 完了前に検証する

完了を主張する前に、[verification](../verification/SKILL.md) の方針で新しい実行結果を確認する。実行したコマンドの終了コードと出力を読み、成功・失敗・未確認を分ける。差分、作業ツリー、意図しないファイル、秘密情報の混入、受け入れ条件の未達を確認する。

実装後のレビューを依頼された場合は [code-review](../code-review/SKILL.md) を別工程として使い、レビュー依頼だけを理由にこの skill が自動修正・commit・PR 投稿を行わない。

### 7. 結果を報告する

変更したファイルと目的、対象外にした変更、実行した検証と対象範囲、未確認事項、次の操作を報告する。commit、push、branch、PR、merge、release などは、ユーザーが明示的に依頼した場合だけ [git-workflow](../git-workflow/SKILL.md) の手順で行う。

## 境界

- レビューだけの依頼では変更しない。レビューは `code-review` の対象とする。
- 失敗の原因究明を主目的とする依頼では、推測で修正を重ねず、再現・切り分け・根本原因の確認を優先する。原因が確定していない場合は、確定した原因として報告しない。診断だけの依頼ではコードを変更せず、原因、証拠、未解決事項を報告する。
- 計画だけの依頼では変更しない。複数段階の計画は `task-planning` の対象とする。
- README、構成説明、相対リンク、ディレクトリ構成の同期も、この skill の責務として扱う。
- commit、push、branch、PR、merge、release の作成・実行は、ユーザーが明示した場合だけ `git-workflow` の手順で行う。
- 破壊的な reset、削除、履歴書き換えは、対象と復旧方法を確認せずに行わない。
