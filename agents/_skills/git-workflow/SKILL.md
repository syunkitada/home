# Git ワークフロー

Git を作業の保存点、変更範囲、履歴、協業境界として扱う。ユーザーが明示した操作だけを実行し、無関係な変更や履歴を壊さない。

## 共通手順

1. `git status --short -uall`、現在のブランチ、追跡先、直近の履歴を確認する。必要なら `git log --oneline --decorate -n 10` で比較元を固定する。
2. `git diff` と `git diff --cached` を分けて読み、未追跡ファイルは個別に内容を確認する。ユーザーの対象範囲と既存の作業、無関係な変更を区別する。
3. 関連する仕様、テスト、レビュー結果、検証結果を確認してから履歴操作を行う。
4. 操作対象、比較元、base/head、生成される履歴、外部へ影響する操作をユーザーに分かる形で確認する。PR や release では参照名だけでなく解決した SHA も記録する。
5. 未コミット変更が失われる可能性、履歴を書き換える可能性、外部状態を変更する可能性を操作前に確認する。
6. 操作後に `status`、diff、log、必要な検証結果を確認し、実際の状態と未確認事項を報告する。

## 操作別の方針

### ブランチ

- 既存の未コミット変更を確認してから作成、切り替え、削除を行う。
- ブランチ名と目的を明確にし、無関係な変更を別のブランチへ混ぜない。
- base は `main` や `master` と決め打ちせず、リポジトリの default branch、upstream、作業の起点から解決する。detached HEAD では起点の SHA を記録する。
- ブランチ名の規約と、ローカル・リモートでの名前の衝突を確認する。
- 切り替えで変更が失われる可能性がある場合は、先に停止して確認を求める。
- ブランチを削除する前に、対象が merge 済みであること、未コミット変更がないこと、他の worktree で使用されていないことを確認する。未 merge の強制削除は明示的な依頼なしに行わない。

### worktree

- ブランチを作成する前に、`git rev-parse --git-dir` と `git rev-parse --git-common-dir` を比較して、既に linked worktree 内で作業していないか確認する。サブモジュールを worktree と誤認しない。
- 新しい worktree はユーザーの意向を確認してから作成する。利用可能なら環境の native な worktree 機能を優先する。手動作成時の配置先は、ユーザー指定、既存の `.worktrees/`、既存の `worktrees/` の順に選び、どちらもなければ `.worktrees/` を既定にする。
- プロジェクト内の `.worktrees/`、`worktrees/` などに作る場合は、配置先が ignore されているか確認し、されていなければ作成を止める。リポジトリ外の明示された配置先は、ignore の有無では止めず、存在・既存 worktree との衝突・権限を確認する。`.gitignore` の変更や作業領域の切り替えを、別の依頼なしに行わない。
- PR 中の worktree や、未コミット・未追跡ファイルを含む worktree を自動で削除しない。削除前に `git status --short -uall` を確認し、`--force` は明示的な依頼なしに使わない。

### コミット

- 一つの論理的な目的ごとに、独立してレビュー・検証できる単位へ小さくまとめる。コミット前に staged diff と、意図的に含める未追跡ファイルを読む。
- メッセージは変更内容ではなく目的が分かる短い命令形にし、リポジトリの規約があれば従う。
- リポジトリに適した秘密情報チェック、テスト、lint、型チェックなどを、変更内容に応じて実行する。コミットが検証済みの保存点になることを優先する。
- ユーザーがコミットを求めていない場合は、コミットを作成しない。

### PR、push、release

- base、head、対象コミット、検証結果、差分の範囲を確認してから作成・更新する。
- push、PR 作成、release など外部状態を変える操作と、merge、tag などローカルの履歴や作業ツリーを変える操作は、ユーザーの明示的な依頼なしに実行しない。
- ローカル merge は merge 後のツリーで検証してから branch を削除する。PR を作成した場合は、フィードバック対応に使えるよう branch と worktree を自動で削除しない。
- release では、プロジェクトが採用する場合に限り version、tag、changelog、成果物の対応を確認し、tag が意図した検証済み commit を指すことを確認する。
- push が拒否された場合は remote の更新理由を調べ、force push で解決しない。force push、履歴書き換え、広範囲の削除や reset は、対象、影響、復旧方法を確認しても、明示的な依頼なしに行わない。

### merge conflict

- まず `git status` で merge または rebase の状態と対象ファイルを確認する。
- commit、PR、issue、仕様などから競合した両側の意図を読み、hunk ごとに比較する。互換する変更は両方を残し、`ours` / `theirs` の機械的な採用や新しい挙動の発明を避ける。
- 解消後に競合マーカー、`git diff --check`、staged diff、関連テストを確認し、merge/rebase が完了したかを確認する。中止や `--abort` はユーザーの意図を確認してから行う。

### 破壊的な操作

- `reset --hard`、`clean`、変更を失う `restore` / `checkout` / `switch`、`branch -D`、`worktree remove --force`、force push、履歴を書き換える rebase や amend は、対象、影響、復旧方法を確認せずに行わない。
- `stash` などで変更を一時退避する場合も、対象と復元方法を記録し、無関係な変更を隠して範囲確認を省略しない。

## 完了時の報告

- 変更したファイル、branch、commit、worktree
- 意図的に触れていない変更と対象外にした理由
- 実行した検証と、その対象 commit またはツリー
- 外部操作の有無、生成された履歴、残っている懸念や未確認事項
