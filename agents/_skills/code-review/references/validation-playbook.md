# 検証手順

指摘候補に追加の証拠が必要なときに使う。確認はリスクと依頼されたレビュー範囲に見合う大きさにする。

## 候補の検証

1. 問題を発生させる最小の入力または状態を記述する。
2. その入力から変更コード、影響を受ける出力または状態までの経路を追う。
3. 呼び出し元、ガード、エラー処理、変更前の挙動を確認する。
4. 既存のテストまたはコマンドのうち、最も狭い有効なものを実行する。
5. テストがなければ、一時的な再現または最小のテスト用データだけを作る。レビューだけの依頼ではリポジトリを変更しない。
6. 結果が観測されたものか、コードから推論したものか、未検証のままかを記録する。

## 証拠の扱い

- 失敗するテストや再現可能なコマンドは強い証拠だが、ユーザーのシナリオと対応する理由を説明する。
- 実行に利用できないサービスや破壊的な準備が必要な場合は、コード経路の証明でもよい。その場合は仮定を明記する。
- テストが通っても、無関係な境界条件の安全性まで証明したことにはならない。
- 仕様未定義の挙動に依存する候補は、確定した不具合ではなく未解決の問いまたは検証不足として報告する。
- 一時ファイルとテスト用データはリポジトリ外に置き、安全な場合は検証後に削除する。

## 完了前の確認

報告前に、すべての指摘が次を満たすことを確認する。

- 到達可能な発生条件
- 原因となる変更行または挙動
- 具体的な影響
- 検証済みの証拠（再現結果、テスト結果、または具体的なコード経路）。未検証の仮定だけの場合は、確定した指摘ではなく未確認事項として分離する
