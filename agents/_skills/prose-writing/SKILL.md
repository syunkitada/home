# 文章作成・編集

読者が目的の情報を理解し、必要な判断や行動へ進める文章を作成・編集する。言語や出力先が変わっても、根拠のない情報を加えず、文章の意味と役割を保つ。

## 発動条件

次のような自然言語の文章・文書を新規作成、編集、翻訳、要約、推敲するときに使う。

- MarkdownのREADME、技術文書、手順書、社内ナレッジ
- 文書内で説明に使うMermaid図の作成・編集
- 技術説明、プロダクト・機能・仕様の説明
- Wiki、議事録、FAQ、判断記録
- Slackなどの依頼、報告、相談、告知
- 「読みやすく」「明確に」「自然な表現に」「AIっぽさを減らして」といった文章の改善

アプリケーションコードや設定の実装、一般的な構造化データの生成、エージェント指示やskill manifestの作成は対象外とする。Mermaid記法は、文書内で説明に使う図表として扱う。リポジトリ変更を含む文書作業では、必要に応じて `implementation` と `verification` を組み合わせる。文章の事実確認を伴う場合は、根拠となる実装・仕様・信頼できる情報源を確認する。

`write`、`edit`、`translate`、`summarize`、`polish` の指定がなければ、素材と依頼から作業を判断する。形式の指定がなければ、用途と出力先から形式を決める。

## 最優先の制約

既存文書を編集するときは、主張、比重、確信度、文の働き（説明・評価・依頼・予定など）を変えない。元の素材や確認済みの情報源にない事実、数値、条件、担当、期限、効果、意見を本文へ加えない。情報が足りない場合は、本文を推測で埋めず、重要な確認事項または明示した前提として分ける。

新規作成では、ユーザーが提供した素材と確認済みの情報源を根拠にする。外部情報を使う場合は、依頼に必要な範囲を調べ、出典や確認日が必要な文書では明記する。技術文書では既存文書だけを正しさの根拠にせず、実装や設定などの一次情報と照合する。

## 作業手順

### 1. 読者、目的、言語、形式を整理する

次を内部で整理する。

```text
読者: 誰が読むか
目的: 読んだあとに何を理解・判断・実行するか
言語: 指定言語、または既存文書の言語
形式: Markdown、Wiki、Slackなど
前提と対象外: 必要な入力、扱わない内容
```

出力を大きく左右する不明点だけ確認する。安全な仮定で進められる場合は、その前提を明示する。

### 2. 根拠と既存の慣例を確認する

- 編集では対象文書と同種の関連文書を先に読む。
- リポジトリの説明では、適用される指示、仕様、実装、設定、既存文書を確認する。名前やディレクトリ構成だけから挙動を推測しない。
- 主メッセージを一文で示せない場合は、素材が足りているか確認する。
- 既存の用語、トーン、言語慣例、文書テンプレート、Markdown方言を優先する。
- 機械向け・外部規約準拠の文書では、その文書固有の形式を保つ。文体や書式の一律適用は避け、ユーザーが依頼した文章部分を中心に編集する。

### 3. 文章と形式を整える

- 読者が必要とする結論、依頼、状況を適切な位置に置く。意図的な構成や既存テンプレートがある場合はそれを尊重する。
- 一文の情報量、段落、見出し、箇条書き、表、リンク、図表を、内容の関係と検索性に合わせて使う。
- 用語は対象読者と既存文書に合わせる。正式名称や定着した専門用語を根拠なく言い換えない。
- 文体や語調は、対象言語、読者、媒体、既存の慣例に合わせる。特定言語の規則を他言語へ適用しない。
- Markdownでは見出し階層、相対リンク、アンカー、コードフェンス、表、図表が対象ホストやプロジェクトの慣例に合うか確認する。Mermaidなどの図は、関係を明確にできる場合に使い、内容が根拠に一致することを確認する。
- AIらしさを理由に定着した表現、専門用語、引用、慣用句を機械的に削除しない。固定的な禁止語や書式規則を、文脈を見ずに適用しない。

### 4. 仕上がりを点検する

[`references/review.md`](./references/review.md) から用途に関係する確認項目を使う。形式別の詳細が必要な場合だけ、該当する参照資料を読む。

## 出力

- 新規作成では完成した本文を先に示し、必要な場合だけ前提・確認事項・不足素材を続ける。
- 編集では修正後の本文を先に示し、変更点は実際に変更した内容だけを簡潔に示す。
- Slackなど貼り付けて使う文章では、本文をそのまま使える形で示し、不要な解説を加えない。
- 本文に入れられない不明点は、重要なものに絞って確認事項として示す。
