# Markdown文書

README、プロジェクト文書、手順書、記事など、人が読むMarkdownの作成・編集に使います。文書内容に加え、見出し、リンク、コード例、表、図表が読者と対象ホストに合うか確認します。

## 作業前

- 適用される `AGENTS.md`、README、既存の同種文書、テンプレート、Markdown lint設定を確認する。
- 技術的な主張、コマンド、バージョン、設定値は、実装・設定・仕様などの根拠と照合する。ディレクトリ名や一般的な慣例から補わない。
- 複数のMarkdownファイルをまとめて編集する場合は、機械向けまたは外部規約があるファイルを見分け、その形式を壊さない。ユーザーが指定した場合も、一般的な文体・レイアウト規則は適用せず、求められた内容を保って編集する。

## 構成と書き方

- タイトルと冒頭で文書の目的や対象読者を把握できるようにする。
- READMEやガイドは、概要、利用開始、主要な仕組み、設定、関連文書などから必要な節を選ぶ。すべての文書に同じ順番や節を強制しない。
- 見出しは内容を正確に表し、階層を飛ばさない。見出しだけを読んでも長文書の要点を追えるか確認する。
- 手順は前提、操作、期待される結果を対応させる。コード例やコマンドは確認できたものだけを示し、説明と実行内容を一致させる。
- 表は項目間の比較や対応関係に、箇条書きは独立した項目に使う。因果関係や条件をリストにして意味を失わせない。
- 図は複雑な関係を明確にできる場合に加える。Mermaidを使う場合は図の各関係が資料や実装で裏付けられていることを確かめる。
- Mermaidの図種選びと構文が必要な場合は、[`../diagrams/mermaid.md`](../diagrams/mermaid.md) を参照する。
- 文書群の案内やIndexが必要な場合は、管理対象と対象外を区別し、各リンクが実在するファイルを指すようにする。

## リンク、翻訳、既存文書の点検

- 相対リンク、URL、見出しアンカーを対象ホストの規則に照らして確認する。見出しを変更したときは、そのアンカーを参照するリンクも確認する。
- 翻訳では、指定された言語と既存のロケール命名規則を優先し、コード、識別子、パスなどを不用意に翻訳しない。原文と翻訳間で見出し・リンク・表・コード例が対応するか確認する。
- 既存文書の整理では、古い情報、リンク切れ、曖昧な用語、重複、根拠のない主張を確認する。変更前に確認が必要な重要な曖昧さがあれば、推測で内容を差し替えない。
- badges、文書マップ、見出しレベル、1コードブロック1コマンド、パスのリンク化などは、プロジェクトの規約や読者の利便性に合う場合に採用する。特定の書式規則をすべてのMarkdownへ一律適用しない。

## 出力前の確認

- 見出しと本文が一致し、不要な節や重複がない。
- 相対リンク、アンカー、Indexが実在する文書と対応する。
- コマンド、コード、表、図が説明と一致し、必要な前提が分かる。
- 対象ホストで読みやすいMarkdownになっており、プロジェクトのlintや慣例に沿っている。
- 文章の変更で、文書が持つ機械的な役割や外部規約を損なっていない。
