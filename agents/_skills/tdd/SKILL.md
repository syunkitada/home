# テスト駆動開発

テストを実装の証拠として使い、RED、GREEN、REFACTOR の短い反復で挙動を変更する。テストは実装の内部構造ではなく、利用者から観測できる結果を固定する。テストを先に書けない場合も、理由、代替の検証方法、残るリスクを明記する。

## 使うとき

- 新しいロジックやAPIの挙動を追加するとき
- バグを修正するとき
- 既存の挙動や境界条件を変更するとき
- リファクタリングで外部から見える挙動を維持することを確認するとき

純粋な文書変更、挙動に影響しない静的な設定変更、生成物の更新だけでは適用しない。設定変更が実際の挙動を変える場合は、設定を含む経路の回帰検証を行う。

## 手順

### 1. 対象の挙動とテスト方法を確定する

仕様、チケット、README、`AGENTS.md`、既存実装、関連テストを読み、変更する外部挙動、利用経路、既存の回帰テストを確認する。README、CI、Makefile、`package.json`、`pyproject.toml`、`go.mod` などから、テストフレームワーク、単一テスト、関連スイート、全体テストの実行方法を調べ、標準コマンドを推測しない。

作業ツリーの既存変更も確認し、別作業のテストや実装を上書きしない。対象が純粋な文書・静的設定・生成物だけなら、この skill を適用せず、構造・リンク・生成物の検証へ切り替える。

### 2. テストシナリオを定義する

要件を、利用者から観測できる一つの挙動へ分解する。入力、操作、期待する状態・結果、エラー、境界条件を明確にし、Arrange、Act、Assert の順で読めるシナリオにする。

テストは実装の内部呼び出しよりも、返り値、状態、出力、永続化結果、外部から見えるエラーなどの結果を検証する。テスト名は「何をすると、どうなるか」が分かる表現にし、一つのテストへ無関係な複数の挙動を詰め込まない。

### 3. RED: 正しい理由で失敗させる

期待する挙動を表す最小のテスト、またはバグを再現するテストを、実装より先に追加する。バグ修正では、まず修正前のコードで不具合を再現する。

最も狭いテストコマンドを実行し、次を確認する。

- テストが失敗または未実装として失敗する
- 失敗理由が期待する挙動の未実装や既存バグである
- テストの記述ミス、環境エラー、依存関係の問題で失敗していない

テストがすぐに通った場合は、変更前の不具合を捕捉できているか、期待値が既存挙動を誤って再記述していないかを確認する。失敗理由を説明できるまで、GREENへ進まない。

### 4. GREEN: 最小限で通す

REDで確認したテストを通すために必要な最小限の実装だけを行う。未要求の一般化、先回りした拡張、無関係なリファクタリングを同時に行わない。テストを通すためにテストの期待値を弱めたり、実装に合わせて挙動を変更したりしない。

同じ最も狭いテストを再実行し、成功したことを確認する。その後、変更経路に直接関係する既存テストを実行し、局所的な成功を回帰の不存在と誤認しない。

### 5. REFACTOR: 挙動を変えずに整える

GREENを確認した後だけ、重複、命名、構造、テストの可読性を改善する。各リファクタリングの後にテストを再実行し、挙動を変えていないことを確認する。

テストでは、可能な限り実際の実装を使う。モックは、外部サービス、非決定的な依存、制御できない副作用など、実装を直接使えない理由がある場合に限定する。モックの呼び出し回数ではなく、利用者が得る結果を優先して検証する。

### 6. 境界、統合、全体を検証する

正常系だけでなく、変更のリスクに応じて空値、境界値、失敗経路、権限、再実行、互換性、統合経路を追加する。テストの規模は、まず高速な単体テスト、必要な境界の統合テスト、重要な利用者経路のE2Eテストの順に選ぶ。

最後に、対象テストスイートとリポジトリが定める型検査、lint、build、全体テストなどを実行する。実行できない場合は、理由、実施した代替確認、未検証の経路、残るリスクを記録する。

### 7. 結果を報告する

RED、GREEN、REFACTORの各段階で実行したコマンドと結果、追加・変更したテスト、対象外の経路、未検証事項、テストできなかった理由を報告する。commit、push、PRなどのGit操作は、この skill の完了条件に含めず、明示的な依頼があれば [git-workflow](../git-workflow/SKILL.md) に分ける。

テストがすぐに通った場合は、テストが変更前の不具合を実際に捕捉しているかを確認してから実装を信頼する。

## 境界

- 計画だけの依頼は [task-planning](../task-planning/SKILL.md) に分け、コードやテストを変更しない。
- 実装全体の調査・構成説明の同期は [implementation](../implementation/SKILL.md) の責務とし、この skill は挙動をテストで固定する部分に集中する。
- 完了を主張するための要件、差分、作業ツリー、未確認事項の確認は [verification](../verification/SKILL.md) と組み合わせる。
- 純粋な文書変更、挙動に影響しない静的設定、生成物の更新にTDDを強制しない。
- commit、push、branch、PR、merge、releaseの作成・実行は、ユーザーが明示した場合だけ [git-workflow](../git-workflow/SKILL.md) の手順で行う。
