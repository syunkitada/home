# テスト駆動開発

テストを実装の証拠として使い、RED、GREEN、REFACTOR の短い反復で変更する。テストを先に書けない場合も、理由と代替の検証方法を明記する。

## 使うとき

- 新しいロジックやAPIの挙動を追加するとき
- バグを修正するとき
- 既存の挙動や境界条件を変更するとき

純粋な文書変更、静的な設定変更、生成物の更新だけでは適用しない。

## 手順

1. README、設定、CI、Makefile、`package.json`、`pyproject.toml`、`go.mod` などから、リポジトリのテスト方法と対象のテストフレームワークを確認する。標準コマンドを推測しない。
2. 要件を、観測可能な一つのテストシナリオへ分解する。
3. RED: 期待する挙動を表す最小のテストまたはバグ再現テストを書き、正しい理由で失敗することを確認する。バグ修正では、修正前に再現を確認する。
4. GREEN: テストを通す最小限の実装を行う。未要求の一般化やリファクタリングを同時に行わない。
5. REFACTOR: 挙動を変えずに重複、命名、構造を改善し、各段階でテストを再実行する。
6. 関連する境界条件、失敗経路、統合経路を追加で検証し、最後に対象のテストスイートとリポジトリが定める全体検証を実行する。
7. RED、GREEN、REFACTOR の各結果、未検証の経路、テストできなかった理由を報告する。

テストがすぐに通った場合は、テストが変更前の不具合を実際に捕捉しているかを確認してから実装を信頼する。
