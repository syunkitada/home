# タスク計画

ユーザーの目的を、実装前に確認できる作業計画へ変換する。要件、受け入れ条件、依存関係、検証方法、未解決事項を整理し、実装へ安全に引き渡せる単位へ分解する。計画だけの依頼では、プロダクトのコード、設定、テスト、コミットを変更しない。

## 使うとき

- 新機能、バグ修正、リファクタリング、設定変更を複数の検証可能な単位へ分けるとき
- 要件、対象範囲、完了条件、実装順序が曖昧なとき
- 既存の構成や利用経路を調べ、依存関係・リスク・実装方針を決める必要があるとき
- 複数の担当者やセッションへ作業を分けるとき

単純な一行修正、すでに作業手順が明確な変更、仕様に検証可能なタスクが十分に定義されている変更には、計画だけの skill として適用しない。実装を行う場合は [implementation](../implementation/SKILL.md)、挙動変更のテスト設計は [tdd](../tdd/SKILL.md)、完了確認は [verification](../verification/SKILL.md) に引き渡す。

## 手順

### 1. 依頼と成果物の範囲を確定する

ユーザーの目的、明示された制約、対象範囲、期限、期待する成果物、計画の承認者を抜き出す。計画を会話で報告するのか、計画文書やタスク一覧へ保存するのかを確認する。保存先の指定がなければ、`tasks/plan.md` や `tasks/todo.md` を勝手に作成せず、会話で計画を報告する。

計画だけの依頼では、プロダクトのコード、設定、テスト、生成物を変更しない。明示的に計画文書の保存を依頼された場合は、その文書の作成だけを行い、実装は開始しない。

### 2. 読み取り専用で根拠を集める

次の順で確認する。

1. ユーザーが指定した仕様、チケット、受け入れ条件
2. 適用される `AGENTS.md`、README、プロジェクト規約
3. 変更対象の既存実装、呼び出し元、設定、データ形式
4. 関連するテスト、CI、ビルド、移行処理、運用手順
5. 既存の計画文書、タスク一覧、作業ツリーの変更

既存の契約、利用経路、変更範囲、検証方法を確認する。未追跡ファイルや別作業の変更を計画へ混ぜず、推測だけでファイルや手順を確定しない。

### 3. 事実、仮定、未解決事項を分ける

調査結果を、確認済みの事実、計画上置く仮定、実装方針を変える未解決事項に分ける。結果や安全性に影響する不明点は仮定で埋めず、質問として残す。実装中に安全に決められる細部は、決定条件とともに計画へ記載する。

### 4. 受け入れ条件を定義する

目的を、実装後に観測できる結果へ変換する。通常の成功経路だけでなく、必要に応じて次を含める。

- エラー、境界値、空値、権限、失敗時の扱い
- 既存利用者・データ・APIとの互換性
- 移行、ロールバック、再実行、安全な中断
- README、設定、データ形式など構成変更に伴う同期

受け入れ条件と、プロジェクト全体の完了基準を混同しない。前者は今回の目的、後者はテスト・レビュー・ドキュメントなど毎回の品質基準として分けて記載する。

### 5. 依存関係、リスク、実装順序を決める

変更対象間の依存関係を調べ、基盤となる変更、高リスクの変更、実装順序、並行化できる作業を明記する。高リスクな検証は早い段階に置く。並行化する場合は、共有するAPI、データ形式、設定などの契約を先に固定する。

作業順は、可能な限り水平方向の層別ではなく、独立して動作・検証できる垂直スライスにする。広範囲の機械的リファクタリングなど垂直スライスにできない変更は、互換形の追加、利用箇所の段階的移行、旧形の削除という順序に分ける。

### 6. タスクを検証可能な単位へ分解する

各タスクに、次の項目を付ける。

- **目的・成果物**: 利用者や後続タスクから見て何が使えるようになるか
- **対象範囲**: 変更するファイル、モジュール、設定、データ、または確認する領域
- **依存関係**: 先に完了している必要があるタスク。なければ「なし」
- **受け入れ条件**: 具体的でテスト可能な条件
- **検証方法**: 実行するテスト、lint、型検査、build、手動確認、リンク確認など
- **規模**: 1回の集中した作業と検証で完了できる大きさか

一つのタスクに無関係な整理や将来向けの一般化を混ぜない。受け入れ条件を短く説明できない、独立した複数サブシステムをまたぐ、複数セッションを要するタスクは、さらに分割する。ただし、分割後も各タスクが作業状態を壊さず、独立して検証できるようにする。

### 7. チェックポイントと引き渡し条件を置く

主要な段階の後に、テスト、build、主要経路、受け入れ条件を確認するチェックポイントを置く。計画の最後に次を確認する。

- すべてのタスクに受け入れ条件と検証方法がある
- 依存関係と実装順序が明確である
- 高リスク箇所を早期に検証できる
- 未解決事項とユーザー判断が必要な点が明記されている
- 実装へ引き渡す前に計画をレビュー・承認できる

計画中に実装上の問題を見つけても、ユーザーが実装を依頼していない限り変更を始めない。commit、push、branch、PR、merge、releaseなどのGit操作は [git-workflow](../git-workflow/SKILL.md) に分ける。

## 出力

計画は、日本語で次の順に報告する。

1. 目的、対象範囲、対象外
2. 前提、確認済みの事実、未解決の質問
3. アーキテクチャや実装方針の判断と理由
4. 依存関係を反映したタスク一覧
5. 各タスクの受け入れ条件と検証方法
6. チェックポイント、リスク、ロールバックまたは移行方針
7. 実装開始の条件と、次にユーザーが判断すること

計画文書を保存する場合は、指定された場所を優先する。`tasks/plan.md` または `tasks/todo.md` を使う場合は、既存ファイルに未完了タスクがないか先に確認する。別の作業に属する未完了計画を、確認なしに上書き、削除、統合しない。

## 境界

- 計画だけの依頼では、プロダクトのコード、設定、テスト、生成物を変更しない。
- レビューだけの依頼は [code-review](../code-review/SKILL.md) の対象とし、計画作成へ置き換えない。
- 実装は [implementation](../implementation/SKILL.md) に引き渡し、計画中に実装を始めない。
- 挙動変更のテスト設計は [tdd](../tdd/SKILL.md)、完了前の確認は [verification](../verification/SKILL.md) に分ける。
- commit、push、branch、PR、merge、releaseの作成・実行は、ユーザーが明示した場合だけ [git-workflow](../git-workflow/SKILL.md) の手順で行う。
- 未完了の別作業を含む計画文書を、対象と復旧方法を確認せずに上書き・削除しない。

計画中に実装上の問題を見つけても、ユーザーが実装を依頼していない限り変更を始めない。
