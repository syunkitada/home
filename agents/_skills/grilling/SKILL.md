# 設計インタビュー

計画、設計、意思決定に含まれる暗黙の前提を見つけ、ユーザーと共通理解を作る。これは実装を始める skill ではない。共通理解を確認した後、実装が必要なら [task-planning](../task-planning/SKILL.md) または [implementation](../implementation/SKILL.md) へ引き渡す。

## 使うとき

- ユーザーが「厳しく検証して」「質問で詰めて」「設計を掘り下げて」などと明示したとき
- 複数の設計判断があり、後続の判断が前の判断に依存しているとき
- 実装前に、目的、対象範囲、制約、失敗時の扱い、未決定事項を整理したいとき

次の依頼には適用しない。

- 単純で手順が明確な修正
- 仕様、受け入れ条件、対象範囲がすでに確定している実装
- ユーザーが質問ではなく、すぐに調査、実装、レビュー、説明を求めている依頼

## 進め方

### 1. 判断の木と範囲を作る

ユーザーの目的、期待する結果、制約、対象外を確認する。必要なら、設計判断をノード、判断の依存関係を枝とする「判断の木」を内部で作る。すでに確認できる事実は、ユーザーに質問する前にファイルや利用可能なツールで調べる。

各判断を次のどれかに分ける。

- **事実**: ファイル、設定、既存の利用経路、仕様などから確認できるもの
- **判断**: ユーザーの目的や優先順位に基づいて決めるもの
- **仮定**: 現時点では確定できず、置くなら明示が必要なもの

### 2. frontier を計算する

前提が確定していて、いま質問できる判断だけを現在の frontier とする。未確定の前提に依存する質問は、後続のラウンドへ送る。事実の確認で解決できる質問は、ユーザーへ投げずに調査する。

### 3. 質問をラウンドで提示する

現在の frontier にある重要な判断を、1ラウンドにまとめて提示する。質問が多い場合は、重要度と依存関係を優先して1ラウンド3〜5問程度に分け、次のラウンドがあることを伝える。各質問には、必要に応じて選択肢と推奨案を付ける。

```text
❓ **Q1 — 質問のタイトル**: 判断したい内容。必要なら選択肢を示す。

➡️ **推奨**: 推奨する選択肢と、その理由。
```

推奨案は判断を代行するものではない。ユーザーが「保留」「後で決める」「今回は対象外」と答えた場合は、その状態を明示的なノードとして記録し、無理に確定させない。質問を提示したら、回答を待ってから次のラウンドへ進む。

### 4. 回答後に木を更新する

各ラウンドの回答を受けたら、次を短く整理する。

- 確定した判断
- 調査で確認できた事実
- 明示した仮定
- 保留または対象外にした判断
- 回答によって新たに開いた frontier

既存の回答と矛盾する回答が出た場合は、影響を受ける判断を開き直す。依存関係を無視して質問を増やさない。

### 5. 共通理解を確認して引き渡す

対象範囲の判断に未解決の重要事項がなくなったら、次の構成で共通理解を要約する。

- 目的
- 対象範囲と対象外
- 確定した判断
- 確認済みの事実と置いた仮定
- 残るリスク、保留事項、未確認事項
- 次に行う作業

ユーザーが確認するまで、コード、設定、テスト、ドキュメント、外部状態を変更しない。確認後、実装が必要なら `task-planning` または `implementation` へ引き渡す。質問だけで完結する依頼なら、要約を最終結果とする。

## 境界

- ユーザーが明示的に求めていないのに、すべての依頼を質問ラウンドへ変換しない。
- ツールで確認できる事実を、ユーザーの記憶や推測に頼らない。
- 推奨案を決定事項として扱わない。
- すべての仮想的な分岐を掘り尽くすのではなく、依頼の対象範囲と結果に影響する判断を扱う。
- 確認前に、質問結果を根拠として実装やファイル変更を始めない。
