# セッション振り返り

現在のセッションで何が起きたかを確認し、次回以降の作業を改善するための候補を提案する。改善候補には既存skill・ツールの更新だけでなく、反復する判断や処理を新規skill・新規ツールへ切り出す案も含める。会話、実行結果、差分、関連する skill・設定・文書に基づいて整理し、根拠のない一般論や、ユーザーの一時的な好みを恒久的なルールへ変換しない。

## モード

- **完了時ライトモード**: 作業が明確に完了したとき、現在の会話と関連ファイルだけを短く確認する。有意な候補がなければ「追加提案なし」と確認範囲だけを示し、追加質問はしない。
- **明示依頼モード**: ユーザーが振り返りや改善案を明示的に求めたとき。指定された対象を含めて通常の手順で調査し、レポートの最後にユーザー確認を1〜2問だけ置く。
- **指定ログモード**: 過去セッションやログのパスが指定されたとき。対象の同定、読み取り量、出典の扱いを [references/session-evidence.md](./references/session-evidence.md) に従う。パスが曖昧な場合は推測で探索しない。

## 発動条件

次の依頼で使う。

- 「振り返って」「レトロスペクティブして」「改善案を出して」など、セッションの振り返りを明示的に求められたとき
- agent skill、agent設定、作業文書、検証、ツール利用の改善、または反復作業を新規skill・新規ツールとして切り出す提案を求められたとき
- 現在の作業が明確に完了し、次回の作業に有意な改善候補がありそうなとき

作業が継続中、失敗の切り分け中、またはユーザーの判断待ちである場合、完了時の自動振り返りは行わない。ただし、明示的な振り返り依頼がある場合は、未完了の状態も対象にして報告する。

完了時の軽量な振り返りでは、改善候補がない場合に長い報告を作らず、「追加提案なし」と確認範囲だけを示す。明示依頼では、候補がない場合も確認した範囲と未確認事項を報告する。

## 手順

### 1. 対象範囲を固定する

- 既定の対象は、現在の会話と、そのセッションで扱った関連ファイル、差分、コマンド結果とする。これらすべてを証拠源として扱い、出力前に同じマスキング規則を適用する。
- ユーザーが skill、ファイル、ディレクトリ、ツール名を指定した場合は、現在のセッションに加えて指定対象を確認する。
- 指定がない過去セッションやログを推測して探さない。過去のセッションを対象にする場合は、ユーザーが指定したログやファイルだけを読む。ログを読む場合は、[references/session-evidence.md](./references/session-evidence.md) の安全な読み取り手順を先に確認する。
- 関連しないリポジトリ全体の整理、外部サービスの調査、広範な一般論の収集は行わない。

### 2. セッションの事実を整理する

次の項目を、確認できた事実として整理する。

- ユーザーの目的、完了条件、対象範囲
- agentが選んだ方針、参照した skill・設定・文書・ツール
- 実行した変更、コマンド、テスト、検証結果
- 失敗、再試行、手戻り、ユーザーからの訂正や追加指示
- 未確認事項、制約、ユーザーが次に判断する必要がある事項

事実と、そこから導いた改善仮説を分ける。実行されなかった手順、確認されていない利用者影響、推測したユーザー意図を事実として扱わない。可能な限りファイルの絶対パスと行番号（`/absolute/path:line`）、会話の発言、またはコマンドの実行結果を根拠として示し、根拠の種類を「観測済み」「過去記録」「未確認」と区別する。数値は記憶で補わず、実行結果から転記する。会話、ファイル、差分、ログ、コマンド、ツール結果など、どの証拠源を引用・転記する場合も、秘密情報・認証情報・個人情報・機密パスを先にマスキングし、判定できない値は原文を再掲せず要約する。

過去ログを扱う場合は、入力の同定と読み取りの安全性を先に確保する。具体的な手順と出典の記録形式は [references/session-evidence.md](./references/session-evidence.md) に委譲する。

### 2.5 既存の対策と重複を確認する

- 候補の対象になりそうな既存 skill、設定、README、検証を確認してから提案する。
- 既存の対策があるのに今回うまく働かなかった場合は、発動条件、案内不足、検証漏れ、適用範囲の違いを分ける。単に同じルールを重ねない。
- 恒久的な変更を提案するには、今回の事実に加えて、同種作業での再発性・影響・一般化可能性を確認する。足りなければ「破棄」または「追加調査」に分類する。

### 2.6 学びの扱いを分類する

各観察を次のいずれかに分類する。分類は、改善候補を無理に恒久化しないための判断であり、分類名だけを根拠に変更を提案しない。

- **破棄・一時的な事実**: 一度限りの好み、偶発的な事情、既存の対策で十分なもの
- **既存skill更新**: 既存 skill の発動条件、手順、境界、出力契約を直すもの
- **新skill候補**: 既存 skill と責務が重ならず、独立した反復作業として一般化できるもの
- **agent設定・ルール**: エージェントの既定動作や判断規約を変えるもの。AGENTS.mdの新規ルールはユーザー合意前に提案だけにする
- **作業文書・README**: 構成説明、導線、仕様、手順を直すもの
- **ツール要望**: 既存ツールの機能・使い勝手の改善、または新規コマンド、MCP、アプリ、外部ツールとして切り出す候補。直接変更しない
- **追加調査**: 出典、再発性、影響、対象の同定が不足し、現時点で恒久化できないもの

### 3. 改善候補を探す

セッションの事実に対応するものだけを、次の観点から確認する。

- **ナビゲーション・情報アクセス**: 必要なファイル、規約、依存関係を見つけにくかったか。READMEや設定に、既存資料への案内を追加すべきか。
- **skill・agent設定**: 発動条件、手順、境界、出力契約が不足または過剰だったか。現在の skill と責務が重複していないか。
- **作業文書・構成説明**: README、Index、相対リンク、仕様、作業文書に、今回の作業を再現するための不足があったか。
- **検証・自動化**: 実際に起きたミスや検証漏れを、既存のテスト・lint・check・hook・CIで検出できたか。既存の検証がある場合は、重複した仕組みを提案しない。
- **エージェント向けルール**: 判断が必要な規約の不足か、機械的に検出できる問題かを分ける。機械的な問題は、文書ルールの追加より自動検査を優先する。
- **ツール利用**: コマンド、MCP、アプリ、外部ツールの呼び出しが過剰、非効率、情報不足だったか。既存ツールの機能追加・使い勝手の改善や、新規ツールとしての切り出しは提案までとし、直接変更しない。
- **不要な指示**: 既存の指示が長いだけでagentの判断を変えていないか。削除や統合を提案する場合は、実際の影響を根拠にする。

改善候補は、次の条件を満たすものに絞る。

- セッション中の具体的な根拠がある
- 次回の同種作業で再発する可能性、影響、または改善効果がある
- 改善対象と変更の方向を具体的に説明できる

一度だけの好み、根拠のない最適化、既存ルールで十分に扱える問題、今回の対象外の問題は候補から外すか、未確認の仮説として明示する。

### 4. 優先度と確信度を付ける

- **高**: 作業の正確性、安全性、再現性を損ない、同種作業で再発する可能性が高い
- **中**: 手戻り、探索コスト、検証漏れを減らせる具体的な改善
- **低**: 利便性や読みやすさの改善で、影響または再発性が限定的

確信度は、**高**（直接の実行結果や複数の事実で裏付けられる）、**中**（事実から妥当な仮説を導ける）、**低**（追加確認が必要）で示す。優先度と確信度を混同しない。

### 5. レポートを作る

短い改善レポートを次の形式で作る。

```markdown
# セッション振り返り

## 結論

今回の作業で確認した全体傾向を1〜2文で示す。

## 改善候補

### [高] 対象: 具体的なskill・設定・文書・ツール

- **分類**: 既存skill更新、作業文書・READMEなど
- **事実・根拠**: 会話、ファイル、差分、コマンド結果など
- **影響**: 次回の作業で起きる問題または削減できるコスト
- **提案**: 変更する方針と、変更しない範囲
- **確信度**: 高・中・低
- **次のアクション**: 実装、追加調査、ユーザー確認など

## 未確認事項

提案の判断に必要だが、今回確認できなかった事項だけを示す。
```

候補は重要度順に並べる。候補が複数あっても、同じ原因に対する重複した提案はまとめる。明示依頼で対象を指定された場合は、指定対象ごとの所見が分かるようにする。

明示依頼モードでは、レポートの末尾に次の確認を短く添える。

1. この整理は今回の体験・意図と一致しているか
2. 一致する場合、次に扱う候補はどれか

完了時ライトモードでは、この確認を省略する。

## 境界

- この skill は改善の提案と実装計画を作る。skill、設定、文書、コード、ツールを直接変更しない。
- 実装を求められた場合は、提案を受け入れ条件と変更単位へ整理し、`implementation` へ引き渡す。検証は `verification`、文章の詳細な編集は `japanese-writing` の責務とする。
- ツール、MCP、アプリ、外部サービスの仕様変更や接続変更は行わない。
- AGENTS.mdへの新しいルール追加は、リポジトリの相談ルールに従い、ユーザーの合意前には実施しない。
- セッションに現れなかった失敗や、改善後の効果を確定した事実として報告しない。
- 会話の振り返りを、ユーザーやagentの人格評価、責任追及、不要な長文の監査記録へ拡張しない。
