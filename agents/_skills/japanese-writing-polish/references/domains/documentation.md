# ドキュメンテーション向け仕様

README、ADR、APIドキュメント、How-to、仕様書など、読者が情報を探したり作業を進めたりするための文書を推敲します。文書の目的や構成を整えますが、元の資料にない仕様、手順、数値、例、判断理由は追加しません。

## 1. 既存の文書規約を優先する

- 既存のREADME、ADR、仕様書、APIドキュメント、プロジェクト規約を確認し、テンプレート、見出し、配置、採番、ファイル形式、用語、表記を合わせる。
- 既存の規約がこの資料の標準構成と異なる場合は、既存の規約を優先し、別の形式を黙って導入しない。
- 規約が見つからない場合だけ、文書種別ごとの以下の指針を構成の初期案として使う。

## 2. 読者と目的を先にそろえる

- 誰が読む文書か、読者に何を理解・判断・実行してほしいかを確認する。
- 文書の冒頭で、対象、目的、適用範囲、前提条件のうち元の資料から分かるものを明確にする。
- 読者が次に取る行動や、読み終えた時点で得る結果が元の資料から分かる場合は、見出しや導入文に反映する。
- 読者、目的、前提が特定できない場合は、本文で創作せず「書き手に確かめたい点」に回す。

## 3. 文書種別に合わせて構成する

### README

プロジェクトやディレクトリの目的、最短の利用開始手順、主要なコマンド、構成、関連資料を、読者が迷わない順に並べます。リポジトリの実際の構成やコマンドを確認できない場合は、存在しない項目を補いません。

### How-to・手順書

前提条件、手順、各手順の期待結果、失敗時の対処、完了条件を明確にします。手順を並べ替える場合も、元の依存関係や条件を変えません。操作の結果が書かれていない場合は、推測で追加せず確認事項にします。

### ADR・設計文書

背景、制約、決定、検討した代替案、トレードオフ、結果や影響を区別します。「決定したこと」と「検討したこと」を混ぜず、推測や将来の予定を確定事項として書き換えません。決定の理由を残す場合も、元の資料にない理由を創作しません。

### APIドキュメント・リファレンス

対象、入力、出力、認証、エラー、例、制約を、元の仕様や実装から確認できる範囲で明示します。宣言された型や説明と実際の挙動が一致していると推測せず、確認できない差分は指摘として分けます。スキーマ生成や実装との整合性検証は、対象プロジェクトの検証手順へ委譲します。

### 仕様書・PR説明・変更履歴

変更前後の挙動、利用者や運用者への影響、互換性、移行や注意点を、元の情報に基づいて整理します。「改善した」「強化した」のような評価語だけで終わらせず、何がどう変わったかを具体化します。変更履歴では、未リリースの予定や内部検討を確定した変更として扱いません。

## 4. 読み手が追える文章にする

- 見出しは「概要」「背景」だけで終わらせず、その節で分かる内容を示す。
- 一つの段落に一つの役割を持たせ、定義、手順、理由、注意点を必要に応じて分ける。
- 用語は文書内で表記を統一し、専門用語が必要な場合は最初に意味や対象を示す。
- 条件、例外、責任主体、対象範囲が元の文から分かる場合は、主語や条件節を省略しない。
- 読者への指示、機能の説明、決定事項、可能性の説明を、同じ文型に押し込めない。
- 定型的な導入、一般論、内容を増やさないまとめを削り、読者が判断や作業に使える情報を残す。

## 5. 情報を増やさずに明確化する

- コマンド、コード、数値、リンク、例、エラー名、責任主体は、元の資料や参照できる事実にないものを追加しない。
- 曖昧さを勝手に狭い意味へ置き換えず、必要な確認事項として残す。
- 断定、推量、義務、可能性の強さを維持する。
- 文書の文章を読みやすくすることと、仕様・実装・リンクの正しさを検証することを混同しない。

## 6. 終了後の確認

次の点を、元の文書と照合して確認します。

1. 読者と目的が、本文から読み取れる範囲で明確になっている。
2. 見出しの順序と段落の役割が、読者の疑問や作業の流れに沿っている。
3. 前提条件、手順、期待結果、制約、例外を、元の資料にある範囲で保っている。
4. 主張、言い切りの強さ、決定と検討の区別を変えていない。
5. 補いたくなったが根拠のない情報を追加せず、必要な確認事項へ分けている。
